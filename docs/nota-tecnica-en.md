# Algebraic Merge Queues: bounding Git rebase conflicts without reading blobs

**Technical note · 2026-11-26 · version 1.2 · DOI [10.5281/zenodo.24570948](https://doi.org/10.5281/zenodo.24570948)**
Companion to `merge-lattice-governor` v0.8.0 (`0e4c38a` + `6.1`), `composicion-core`,
`py-test-shadow-guard`. All numbers were produced by the commands in §7 on a disposable clone;
no figure in this note is an estimate.

---

## Abstract

A merge queue is usually treated as a scheduling problem — in what order do we land these
branches? We show that the expensive part is decidable *before* any merge, from tree metadata
alone, by comparing **rename classes** instead of file names. On a live queue of 62 branches
against a real trunk, the prescription had **9/9 correct "no risk" verdicts, zero false
safes**, and its 46 predicted conflicts materialised on **109 paths of which 1 (0.9%) fell
outside the declared classes**. We then report three ways the same measurement lied while looking
healthy: a denominator that named a dead population, an instrument (`git rebase` without
`--rebase-merges`) whose flattening fabricates conflicts the repository does not have, and — the
sharpest — a bound computed over the net diff whose act replays the commit graph. Removing a git
flag that cost 32× per diff changed 0 of 137 verdicts and covered 0 of the 67 conflict paths that
22 real rebases produced.

## 1. The question and its cost

Given branches `B₁…Bₙ` and a trunk `T`, "in what order do they land?" is answered today by
`N(N−1)/2` trial merges or by landing them and discovering the cost in CI. Both are linear in
the wrong quantity: the collision is a property of the *rename classes* each branch touches,
not of the pairs.

## 2. The law

Group every path by its **rename class**: for a diff `T..B`, two names are in the same class iff
`git diff -M --find-copies-harder` reports a rename (or copy) between them, transitively
(union-find). Let `C(B)` be the set of classes whose paths the branch changes and whose paths the
trunk also changed. Then:

> **`C(B) = ∅` ⇒ rebase of `B` onto `T` produces no textual conflict.**

This is a *bound*, not an equality: `C(B) ≠ ∅` lists what *may* collide, not what will.

The name-based version of the same predicate is false. Measured on the ten oldest open PRs of
`psf/requests`: comparing **names**, 11 of 17 real rebase conflicts fell outside the prediction
(the trunk had renamed `requests/models.py` → `src/requests/models.py`; the branch touched the
old name, so the name sets looked disjoint). Comparing **classes**: 0 of 17 outside. On our own
queue: 0 of 10. Total: **27 branches, 27 conflicts, 0 escapes** — but only after the
correction, which is the point.

## 3. The queue, with the population declared

The first census reported, over 309 `origin/worker/*` refs: 17 `AL_DIA`, 224 (72.5%)
`REBASAR_LIBRE`, 68 `REBASAR_CON_RIESGO`. That 72.5% was a **population artifact**. Of the 275
local refs, 213 are ancestors of the trunk (`git merge-base --is-ancestor`): no own commits,
empty diff, zero classes — "safe to rebase" for the only reason a dead branch is safe. The live
queue is **62**.

`SIN_TRABAJO` (`git rev-list --count T..B == 0`) now names that condition and is emitted before
`AL_DIA`, since "contains the trunk" and "contains the trunk and has work of its own" are
different statements.

| state (275 local refs) | v0.6.0 | v0.6.1 |
|---|---|---|
| `SIN_TRABAJO` (already in the trunk) | — | **213** |
| `AL_DIA` | 7 | 7 |
| `REBASAR_LIBRE` | **215** | **2** |
| `REBASAR_CON_RIESGO` | 53 | 53 |

**Two populations, not one.** The census published in v0.6.0 enumerated **309** worker refs in
the disposable clone — 34 more than the 275 the working tree carries — reporting `AL_DIA` 17 ·
`REBASAR_LIBRE` 224 · `REBASAR_CON_RIESGO` 68. In *that* frame the refs already contained in the
trunk number **218** (measured: `git rev-list --count trunk..ref == 0`), so v0.6.1 publishes
**218** `SIN_TRABAJO`, **6** `REBASAR_LIBRE` and **91** live branches. The table above is the
working-tree frame (275 · 213 · 62), which is the one actually rebased. Both counts are correct
and name different populations; publishing a single "the" figure was the defect.

## 4. Against the real act, not an oracle

62 live branches, disposable clone, `git rebase --rebase-merges 34ee1d2c8`:

| prescribed | n | rebased clean | conflicted |
|---|---|---|---|
| `AL_DIA` | 7 | **7** | 0 |
| `REBASAR_LIBRE` | 2 | **2** | 0 |
| `REBASAR_CON_RIESGO` | 53 | 7 | **46** |

- **9/9** "no risk" verdicts respected; **0 false safes**.
- The 46 conflicted branches published **109 unmerged paths; 1 outside the declared classes**
  (0.9%) — a *new* append-only ledger block, not a code path.
- **25 of 46** conflicts involve accounting files only; `INDICE_PLATINO.md` alone appears in
  **20 of 46**, and it is generated by `tools/indice_platino.py`, so those conflicts are
  regenerable by construction. That is a property of this corpus, not of the instrument, and it
  is deliberately **not** encoded in the tool.

Later, on the same branches with the corrected batching relation (§6), the post-rebase pair
matrix over the 15-branch queue gave **9/9** declared-safe pairs merged clean and **1/1**
declared-unsafe pair conflicting on the exact declared file.

## 5. Second trap: the instrument had a frame of its own

Three `AL_DIA` branches — `merge-base` equal to the trunk, nothing to replay — came back in
conflict on an append-only ledger file. The cause was the instrument: `git rebase` **without**
`--rebase-merges` flattens the branch's history and re-applies commits the trunk already
contains. Re-run with `--rebase-merges`: `rc=0`, zero unmerged paths, on exactly those three
branches and no other change in 62. A conflict that no merge would ever produce is not a
property of the repository.

## 6. Third trap: the bound and the act were not functions of the same object

The prescription was slow — 561 s over 155 live branches — and the profile named one git flag:
`--find-copies-harder` in the rename detection, 3 283 ms per diff against 101 ms without it. We
removed it and then measured what it had been buying.

Same 155 live branches (`git rev-list --count T..B > 0`), same binary, same cache: **561 s → 40 s**
(209 s with the flag restored), and **0 of 137 verdicts changed** — `AL_DIA 18 · REBASAR_LIBRE 9 ·
REBASAR_CON_RIESGO 128` in both runs, the flagged run reproducing the previous release's output
byte for byte. What does move is the class list of **22 of the 137** branches, which narrows: a
copy only the flag could see had been entering the rename class as if it were an edge.

Whether that narrowing costs coverage is not a reasoning question. We rebased those 22 for real
(`git rebase --rebase-merges` onto the measured trunk, `--shared` clone): all 22 conflict, **67
paths** in conflict. Inside the wide bound: **3**. Inside the narrow bound: **the same 3**. Paths
covered only by the wide bound: **0**. The flag bought 5.2× of wall clock for zero coverage; it
survives as an explicit opt-in.

The three paths the bound cannot see are the load-bearing part, because they are exactly the paths
a *net diff* cannot see either:

> The prescription is a function of the net diff `base..ref`; the act replays the commit graph.
> Every path where the two disagree is a path present in `git log --name-only` and absent from
> `git diff --name-only` — a file created and deleted inside the branch — or a conflict that only
> exists inside a merge the replay re-executes.

This is the sharpest frame error in the note: the bound and the act were never measuring the same
object. It also explains why `REBASAR_LIBRE` remains a proof — no commit to replay means no path to
see — while a `REBASAR_CON_RIESGO` list is what *may* collide, never what will.

### 6.1 Correction (v0.8.0): that last sentence was one condition short

The sentence above was a *testable* claim, so we tested it on two subjects this repository does not
own. Population and protocol: every branch with work to land (`rev-list --count T..B > 0`) in
`~/primer` (56), the 40 most recently updated open PRs of `psf/requests` (40) and the corpus itself
(114) — **210 branches**, each rebased for real (`git rebase --rebase-merges`, first stop, throwaway
`--shared` clones, `rerere` disabled), verdicts frozen before the act.

| prescribed | n | clean | conflict |
|---|---|---|---|
| `REBASAR_LIBRE` with `rev-list --merges --count base..ref == 0` | 22 | **22** | 0 |
| `REBASAR_LIBRE` with an internal merge | 1 | 0 | **1** |

The counterexample is `psf/requests` `pr/7065`: `REBASAR_LIBRE`, and the replay stops with three
conflicts (`src/requests/adapters.py`, `src/requests/models.py`, `tests/test_adapters.py`). The
branch is 20 commits behind, touches those three paths, and the trunk's net change since the
`merge-base` is ten `.github/*`/config files — the classes are genuinely disjoint. The stop is
reported on the **merge commit**, `Could not apply fe0853c6… Merge branch 'main' into edit-14`, and
that merge is *evil*: `git merge-tree 5547eef 6f66281a` — its own two parents — conflicts on the
same three paths. The resolution lived in the merge's tree, and a merge is not re-applied, it is
re-executed.

So the correct statement is narrower:

> With a linear branch, every commit the replay applies has `base` as its own base, so a path in
> neither net diff cannot collide. With a merge inside `base..ref` the effective base of the
> replayed commits is **older** than the `merge-base`, and the conflict can land on a path neither
> net list publishes as common. `REBASAR_LIBRE` therefore requires *linear history*, not just
> disjoint classes.

v0.8.0 adds `REBASAR_CON_MERGE_INTERNO`: same disjoint classes, plus the count of internal merges and
the branch's own paths, no proof claimed. Cost of the guard: one `rev-list --merges --count`, paid
only by branches that were about to be called free — 4 of 114 in the corpus. Coverage does not move:
**235 conflict paths across the three subjects, 233 inside the path-level bound, 234 inside a class**
(the two misses are a trunk rename that the class sees, and a `BITACORA/bloque-*.md` created on both
sides with different names, which no rename class can join).

The displacement itself was paid down too: two `git rev-list --count` calls became one
`--left-right --count`, **57 ms against 228 ms**, identical field by field.

## 7. Batching: the same law one level up

After rebasing, all branches share the trunk as a **single common base**, and a three-way merge
with one base cannot conflict between change sets on disjoint files. So the graph whose edge is
"shares a path" colour-classes into batches that can be merged *and tested* in one CI run, at
the cost of one `diff` per branch instead of `N(N−1)/2` merges.

The precondition is the expensive part, and it is printed in the output: the relation is a
statement about **post-rebase** merges. Measured against **pre-rebase** pairs — each branch
carrying its own base — it publishes **40 false "safe" pairs out of 105** on the 15-branch
queue, because the collision is with the trunk, not with the other PR.

## 8. Reproducibility

```bash
git clone https://github.com/alexisromtz-lab/merge-lattice-governor && cd merge-lattice-governor
python3 -m unittest discover -s tests -t .          # 138 tests, zero dependencies

# the act each branch asks for, without reading a blob
merge-lattice-governor --base origin/main --prescribir --sin-plan --ref origin/branch-a

# batches that can share one CI run
merge-lattice-governor --base origin/main --lotes --ref a --ref b --ref c
```

The rebase census itself is a `git rebase --rebase-merges <trunk>` loop in a disposable clone
(`git clone --shared`), recording `rc` and `git diff --name-only --diff-filter=U`.

## 9. Limits, stated

- The law is a **bound**, and it is per path, not per hunk: two branches touching the same file
  on different lines merge clean but are counted unsafe.
- A `merge=<driver>` in `.gitattributes` runs inside the real merge and is not executed here:
  those pairs are reported `NO_MEDIDO` **with the driver's name**, never as clean.
- The 24/24 sample published in v0.6.0 is correct and **non-discriminating**: 213 of the 215
  branches it was drawn from were already in the trunk.
- Percentages in this note name their population; where the population changed, both numbers are
  published rather than the survivor.

## 10. What generalises

The transferable object is not the tool but the check: *every metric must publish the frame it
was measured in* — the external ceiling of a debt ratio, the per-pair merge base of a support
relation, the rebase precondition of a batching relation, the population of a percentage, and a
bound and an act that were not functions of the same object. Five occurrences of one family in a
single codebase, each found by measuring rather than reasoning.
